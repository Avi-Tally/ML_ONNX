## Executive Summary
Today's session focused on resolving performance and timeout issues when fetching voucher records from Tally. We migrated from extracting raw, un-filtered `Day Book` dumps in Python to pushing the computation down to Tally's engine using custom TDL `<COLLECTION>` definitions, dynamic filtering, and `<MAX>` limitations. Additionally, we optimized the active port discovery mechanism to aggressively cache active Tally listener ports, drastically reducing latency for consecutive queries.

## Accomplishments & Features Built

### 1. TDL XML Payload Optimization (`fetch_recent_vouchers`)
- **Summary**: Refactored the `fetch_recent_vouchers` payload to construct a custom `VchCollection`. Integrated dynamic TDL `<FILTER>` definitions utilizing native functions (e.g., `$$IsSales:$VoucherTypeName`) and restricted serialization overhead via targeted `<FETCH>` and `<MAX>` tags.
- **Touched Files**: `tally_client.py`
- **Key Implementation Snippet**:
  ```python
        payload = f"""<ENVELOPE>
    <HEADER>
        <VERSION>1</VERSION>
        <TALLYREQUEST>Export</TALLYREQUEST>
        <TYPE>Collection</TYPE>
        <ID>VchCollection</ID>
    </HEADER>
    <BODY>
        <DESC>
            <STATICVARIABLES>
                <SVEXPORTFORMAT>$$SysName:XML</SVEXPORTFORMAT>
                <SVCOMPANY>{company_name}</SVCOMPANY>
                <SVCURRENTCOMPANY>{company_name}</SVCURRENTCOMPANY>{sv_dates}
            </STATICVARIABLES>
            <TDL>
                <TDLMESSAGE>
                    <COLLECTION NAME="VchCollection" ISINITIALISE="Yes">
                        <TYPE>Voucher</TYPE>
                        <SORT>Default : -$Date</SORT>
                        <MAX>50</MAX>
                        <FETCH>Date, VoucherTypeName, VoucherNumber, PartyLedgerName, Narration, Amount, AllLedgerEntries.List, LedgerEntries.List</FETCH>
                        {filter_tag_str}
                    </COLLECTION>
                    {filter_def_str}
                </TDLMESSAGE>
            </TDL>
        </DESC>
    </BODY>
</ENVELOPE>"""
  ```
- **Rationale / Design Notes**: Python's `xml.etree.ElementTree` is too slow to parse multi-megabyte `Day Book` dumps containing nested ledger entries for thousands of unrelated vouchers. Pushing projection, filtering, and limiting into TDL memory drastically shrinks the network footprint.

## Technical Decisions & Trade-offs
- **Custom Filters over `Day Book` Export**: Instead of using `<ID>Day Book</ID>`, we instantiate a fresh `<TYPE>Voucher</TYPE>` collection inline. This is slightly more verbose in TDL XML but offers strictly typed programmatic control over filtering without relying on UI-based variables.
- **Usage of `UMANAME` in Formulae**: We discovered that Tally ignores dynamic formulae defined with `NAME=...` in request payloads, requiring `UMANAME=...` to properly apply the filters to the collection.
- **Date parsing strictness**: Implemented `_to_tally_date()` within `tally_client.py` to rigorously convert ISO strings into the `YYYYMMDD` format strictly required by Tally's `$$Date` macros and `<SVFROMDATE>`.
